# T7 · 验证 — 执行协议

## 触发条件
- 用户说"帮我验证这些 Persona"
- T6 完成后用户选择了验证
- 用户提供了已有 Persona 文档要求审查

## 输入
- Persona 文档（必须）
- 原始数据来源描述（可选——帮助判断数据支撑程度）

## 执行步骤

### Step 1：多维度审查

对每个 Persona 逐一检查以下维度：

```markdown
## Persona 审查清单

### 1. 数据支撑度
- [ ] 每个行为描述都有数据/访谈支撑？
- [ ] 引语来自真实受访者（而非虚构）？
- [ ] 市场占比有量化依据？

### 2. 行为区分度
- [ ] 用 2-3 个变量就能区分各 Persona？
- [ ] 没有两个 Persona "太像"难以区分？
- [ ] Primary Persona 的需求和 Secondary 有明确差异？

### 3. 命名偏见检查
- [ ] 命名是否中性（不含价值判断）？
- [ ] 是否避免了刻板印象（性别/年龄/地域）？
- [ ] 照片/描述是否包容多样性？

### 4. 覆盖度
- [ ] 是否有"哪个 Persona 都对不上"的已知用户？
- [ ] 是否遗漏了重要的用户群体？
- [ ] Negative Persona 是否被明确标注？

### 5. 可操作性
- [ ] 每个 Persona 都能指导具体产品决策？
- [ ] "对产品的启示"足够具体（不是"做好用户体验"这种空话）？
- [ ] 团队看完能说出"如果只满足一个人，选谁"？

### 6. 内部一致性
- [ ] 目标和行为逻辑自洽？
- [ ] 痛点与行为匹配？
- [ ] 场景故事与结构化信息一致？
```

### Step 2：产出审查报告

## 产出模板

```markdown
## Persona 审查报告

### 总体评估：[通过 / 需修改 / 需重做]

### 各 Persona 审查结果

#### [Persona 1 名称]
- ✅ 通过项：[列出]
- ⚠️ 需关注：[具体问题 + 修改建议]
- ❌ 需修复：[具体问题 + 修改建议]

#### [Persona 2 名称]
- ...

### 跨 Persona 问题
- [如果有系统性问题——比如"所有 Persona 的痛点太相似"]

### 修改建议优先级
1. [最重要的修改]
2. [次要修改]
3. [可选优化]

### 验证方案建议
- **最快验证**（1-2天）：找团队里直接接触用户的人（客服/销售），让他们看 Persona 卡片回答"你接触的用户里，能对应到这些人吗？比例感觉对吗？"
- **标准验证**（1周）：每个 Persona 找 2-3 个新用户做 30 分钟快速访谈，验证行为描述是否准确
- **严格验证**（2周）：让新用户做"自我归类测试"——看到去掉名字的 Persona 描述，选自己最像哪个
```

### Step 3：如果需要修改，直接修改

不是给建议——直接产出修改后的版本。如果审查发现问题，直接重写有问题的 Persona 卡片部分，标注修改点。

审查通过或修改完成后：
