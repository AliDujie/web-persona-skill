# 08 — 应用：怎么用、怎么推广、怎么不让它死掉

---

## 一、这是最重要的一章

做 Persona 的目的不是拥有一份文档——是**改变团队的决策方式**。90% 的 Persona 项目死在"做完了束之高阁"。本章解决的就是这个问题。

---

## 二、Persona 的六种核心应用场景

### 2.1 功能优先级决策

```
场景：产品 backlog 里有 20 个需求，只能做 5 个

做法：
1. 每个需求标注"主要服务哪个 Persona？"
2. 按 Primary Persona 优先级排序
3. 如果某需求只服务 Supplemental Persona → 降级
4. 如果某需求让 Primary Persona 体验变差 → 否决
```

**示例表格**：

| 需求 | 服务的 Persona | 优先级 | 决策 |
|------|-------------|--------|------|
| 智能比价 | 精算旅行家（Primary） | P0 | ✅ 做 |
| 社交分享 | 体验探索者（Secondary） | P1 | ✅ 做 |
| 积分商城 | 全部 | P2 | ⏸️ 下期 |
| 游记编辑器 | 体验探索者（Secondary） | P2 | ⏸️ 下期 |
| 竞价排名 | 无（平台收入驱动） | - | ❌ 伤害 Primary |

### 2.2 设计评审

```
场景：设计方案评审会

做法：
1. 评审前明确"这个设计是为哪个 Persona？"
2. 评审中用 Persona 视角审视：
   · "[精算旅行家]看到这个页面，第一反应是什么？"
   · "[精算旅行家]能在 3 秒内找到价格比较入口吗？"
   · "这个设计会不会让[信任型用户]觉得太复杂？"
3. 评审后记录：哪些修改是基于 Persona 洞察做的
```

### 2.3 内容与营销策略

| Persona | 触达渠道 | 内容策略 | 关键诉求 |
|---------|---------|---------|---------|
| 精算旅行家 | 比价类社区、省钱公众号 | 攻略、比价技巧、限时优惠 | "帮你省钱" |
| 体验探索者 | 旅行 KOL、小红书 | 独特体验故事、小众目的地 | "别人没去过的地方" |
| 信任型跟随者 | 朋友推荐、口碑传播 | 用户评价、老用户故事 | "靠谱" |

### 2.4 技术架构决策

```
场景：技术团队在设计推荐算法

做法：
· 精算旅行家 → 推荐低价选项、展示比价信息
· 体验探索者 → 推荐独特/小众选项、突出体验差异
· 信任型跟随者 → 推荐高评分、好评多的选项

不同 Persona 的推荐策略不同 → 需要个性化推荐引擎
```

### 2.5 用户体验写作

| Persona | 文案风格 | 示例 |
|---------|---------|------|
| 精算旅行家 | 直接、突出价值 | "已为你找到最低价，比昨天降了 ¥40" |
| 体验探索者 | 情感化、激发好奇 | "94% 的游客不知道这个隐藏入口" |
| 信任型跟随者 | 权威、安心 | "10000+ 用户好评，无理由退改" |

### 2.6 路线图规划

将 Persona 需求映射到季度 OKR：

```python
# 使用 persona/okr_bridge.py
from persona.okr_bridge import OKRBridge

bridge = OKRBridge()
plan = bridge.derive_okrs(persona_profiles)

# 输出示例：
# Objective: 降低精算旅行家的决策成本
#   KR1: 比价功能使用率从 15% → 40%
#   KR2: 预订转化时长从 3天 → 1天
#   KR3: 比价相关 NPS 从 -5 → +20
```

## 三、推广：让全团队用起来

### 3.1 推广不是"发文档"

| 无效的推广 | 有效的推广 |
|-----------|-----------|
| 发一封邮件附 PDF | 做一次 45 分钟的沉浸式工作坊 |
| 贴在墙上的海报 | 融入每周的设计评审流程 |
| Confluence 里的一个页面 | 在 Jira/TAPD 的 ticket 模板里加 "Target Persona" 字段 |

### 3.2 推广三步法

```
Step 1 · 启动会（一次性）
├── 45 分钟工作坊
├── 每个 Persona 由一个团队成员"认领"并介绍
├── 现场做一次"用 Persona 做决策"的练习
└── 产出：每人说一句"这对我的工作意味着什么"

Step 2 · 嵌入流程（持续）
├── 需求文档模板加"Target Persona"必填字段
├── 设计评审议程加"Persona Check"环节
├── Sprint Planning 时标注每个 Story 的 Persona
└── 数据看板按 Persona 分列

Step 3 · 保鲜（长期）
├── 每月分享一个"Persona 指导了这个决策"的案例
├── 新人 On-boarding 包含 Persona 培训
├── 每季度做一次 Persona 健康检查
└── 当有人说"用户想要…"时追问"哪个 Persona？"
```

### 3.3 "仪式感"技巧

这些小技巧能让 Persona 在团队日常中保持存在感：

| 技巧 | 做法 |
|------|------|
| 物理可见 | 每个 Persona 的海报/卡片挂在工位附近 |
| 语言习惯 | 讨论时用 Persona 名字而非"用户"（"李薇会怎么想？"） |
| 角色扮演 | Sprint Review 时一人扮演一个 Persona 体验新功能 |
| Persona 日 | 每月一天用特定 Persona 的视角审视产品全流程 |
| 新数据更新 | 有新的用户数据时更新 Persona 的"近况" |

## 四、常见死法和防治

### 4.1 Persona 的五种死法

| 死法 | 症状 | 根因 | 防治 |
|------|------|------|------|
| 束之高阁 | 做完没人看 | 没嵌入决策流程 | Step 2 嵌入流程 |
| 众说纷纭 | 每个人理解不同 | Persona 描述模糊 | 用具体行为描述，避免空泛标签 |
| 政治工具 | 被用来支持已有立场 | 没有 Primary 优先级 | 明确优先级 + 用数据说话 |
| 过时失效 | 市场变了 Persona 没变 | 缺少更新机制 | 每 6-12 月健康检查 |
| 太多太碎 | 7+ 个 Persona 记不住 | 贪多 | 控制在 3-5 个 |

### 4.2 最危险的信号

> 当你在会议上听到"用户想要X"而没人追问"哪个用户？"——你的 Persona 已经死了。

## 五、度量：Persona 项目本身的成效

如何证明"做 Persona 值得"？

### 5.1 过程指标

| 指标 | 衡量方法 | 健康值 |
|------|---------|--------|
| 引用频率 | 每周设计评审/Sprint 中提到 Persona 几次 | ≥ 3 次/周 |
| 决策影响 | 有多少产品决策明确引用了 Persona | ≥ 1 次/Sprint |
| 团队认知 | 随机问团队成员能否说出 Primary Persona 的核心特征 | 80%+ 能回答 |

### 5.2 结果指标

| 指标 | 做法 |
|------|------|
| Primary Persona 的满意度/NPS | 监控是否持续提升 |
| 功能采纳率 | 专为特定 Persona 设计的功能使用率 |
| 转化率/留存率 | 按 Persona 分列看是否有针对性改善 |
| 决策速度 | 有 Persona 后功能讨论是否更快达成共识 |

```python
# 使用 persona/measurement_toolkit.py
from persona.measurement_toolkit import MeasurementToolkit

toolkit = MeasurementToolkit()
toolkit.ingest_nps(persona="精算旅行家", score=42, n=150)
toolkit.ingest_nps(persona="体验探索者", score=35, n=80)

report = toolkit.report_okr_progress()
print(report)
```

## 六、跨团队协作

### 6.1 与不同团队共享 Persona

| 团队 | 他们关心什么 | 如何呈现 |
|------|------------|---------|
| 高管 | 市场规模、商业价值 | 突出占比 + 商业机会 |
| 开发 | 具体需求、技术约束 | 突出行为模式 + 使用场景 |
| 市场 | 触达方式、传播策略 | 突出渠道偏好 + 决策因素 |
| 客服 | 常见问题、沟通方式 | 突出痛点 + 语言风格 |
| 数据 | 可量化特征、细分规则 | 突出可操作化的分群标准 |

### 6.2 不同层次的 Persona 文档

| 层次 | 内容 | 受众 | 格式 |
|------|------|------|------|
| 一句话版 | 名字 + 核心描述 | 全公司 | Slack/钉钉 Pin |
| 卡片版 | 核心四要素（目标/行为/痛点/机会） | 项目团队 | A5 卡片/海报 |
| 完整版 | 全部信息含数据和叙事 | 研究和设计团队 | 在线文档 |
| 数据版 | 可操作化的分群规则 | 数据和技术团队 | 表格/代码 |

## 七、本章核心要点

1. **做完 Persona 才是开始**——真正的价值在应用而非文档
2. **嵌入流程 > 发文档**——让 Persona 成为决策过程的必经环节
3. **用 Persona 名字代替"用户"**——语言习惯改变思考习惯
4. **持续保鲜**——每 6-12 月健康检查，Persona 是活的文档
5. **度量 Persona 项目本身的效果**——证明投入值得
6. **最危险的信号是沉默**——没人提 Persona 说明它已经死了
