> **Tier F · 体验地图与叙事**｜关键词：Journey Map、Service Blueprint、Experience Map、Alignment Diagram、Spatial Thinking

## 一、核心定位

Kalbach 是"体验地图"领域的权威参考手册。Persona 回答"是谁"，Journey Map 回答"经历了什么"——两者必须联动。本书系统梳理了 **10+ 种地图类型**，并给出"什么场景用什么图"的决策逻辑。

### 1.1 Persona × Map 联动关系

| Persona 回答 | Map 回答 |
|---|---|
| 这个人是谁？（属性+动机） | 这个人经历了什么？（时间线+情绪+触点） |
| 为什么这样做？（Goal/Pain/Gain） | 在哪一步最痛？什么触发了下一步？ |
| 有几类人？（Segments） | 每类人的旅程有何不同？ |

---

## 二、Alignment Diagram 总框架

Kalbach 把所有体验地图统称为 **Alignment Diagram**——将个人体验与组织能力对齐的可视化：

```
┌──────────────────────────────────────────────┐
│          Individual's Experience              │  ← 用户视角
│   (phases → actions → thoughts → feelings)   │
├──────────────────────────────────────────────┤
│          Organization's Support              │  ← 企业视角
│   (touchpoints → channels → processes)       │
└──────────────────────────────────────────────┘
```

## 三、地图类型决策矩阵

### 3.1 十种主要图型

| 图型 | 视角 | 粒度 | 最佳用途 |
|---|---|---|---|
| Experience Map | 通用人类活动 | 高层抽象 | 战略探索、市场定义 |
| Customer Journey Map | 特定 Persona + 特定场景 | 中粒度 | 优化已知旅程 |
| Service Blueprint | 组织后台 + 前台 | 细粒度 | 服务设计、流程改进 |
| Mental Model Diagram | 认知任务层次 | 深层心智 | 内容策略、IA |
| Empathy Map | 单人/单 Persona | 四象限 | 快速建立共情 |
| Spatial Map | 物理空间体验 | 位置+动线 | 零售/场馆/机场 |
| Ecosystem Map | 多角色关系 | 系统级 | 平台设计、利益相关者 |
| Isometric Map | 3D 空间+时间 | 复合 | 多渠道/全渠道 |
| Job Map (JTBD) | 功能Job 8 步 | 任务级 | 创新机会发现 |
| Wardley Map | 价值链演进 | 战略 | 技术/商业决策 |

### 3.2 选择决策树

```
你的目标是什么？
├── 理解当前用户体验 → Customer Journey Map
├── 优化服务交付流程 → Service Blueprint
├── 探索新市场/战略方向 → Experience Map
├── 理解用户认知结构 → Mental Model Diagram
├── 快速建立团队共情 → Empathy Map
├── 优化物理空间体验 → Spatial Map
└── 分析多角色系统 → Ecosystem Map
```

## 四、Customer Journey Map 详解

### 4.1 标准五行结构

| 行（Row） | 内容 | 数据来源 |
|---|---|---|
| Phases | 旅程阶段（Awareness→Consider→Purchase→Use→Renew） | 业务定义 |
| Actions | 用户在每阶段的具体行为 | 访谈/日志/分析 |
| Thoughts | 每步的内心想法/疑问 | 访谈 verbatim |
| Feelings | 情绪曲线（高兴↗/焦虑↘/困惑↘） | 访谈+推断 |
| Touchpoints | 每步接触的渠道/界面/人 | 全渠道审计 |

### 4.2 增强行（可选）

| 扩展行 | 用途 |
|---|---|
| Pain Points 行 | 标记每步的摩擦/障碍 |
| Opportunities 行 | 创新机会标记 |
| Metrics 行 | 每步关联的 KPI |
| Backstage 行 | 组织内部谁在支持 |
| Moments of Truth | 关键决策时刻标记 |

### 4.3 一个 Persona、多条旅程

```
Persona: "效率达人小王"
  ├── Journey 1: 首次注册
  ├── Journey 2: 日常使用
  ├── Journey 3: 遇到问题求助
  └── Journey 4: 续费/流失决策
```

## 五、Service Blueprint 详解

### 5.1 五条横线

```
┌─────────────────────────────────────────────┐
│ Customer Actions（用户可见行为）              │ ← 用户视角
├─── Line of Interaction ────────────────────┤
│ Frontstage Actions（员工/系统与用户的交互）    │
├─── Line of Visibility ─────────────────────┤
│ Backstage Actions（用户看不到的操作）         │
├─── Line of Internal Interaction ────────────┤
│ Support Processes（IT/物流/财务后台支撑）     │
├─── Line of Implementation ─────────────────┤
│ Infrastructure（技术系统/数据/API）           │
└─────────────────────────────────────────────┘
```

### 5.2 Blueprint × Persona 应用

- 不同 Persona 的 Customer Actions 行不同 → 生成不同的 Blueprint 版本
- Backstage 瓶颈通常是"所有 Persona 都卡"的共性问题 → 优先修复
- Frontstage × Persona = 个性化服务设计的切入点

## 六、Moments of Truth (MoT)

### 6.1 五类关键时刻

| MoT 类型 | 定义 | 来源 |
|---|---|---|
| Zero Moment (ZMOT) | 搜索/研究阶段第一次接触品牌 | Google 提出 |
| First Moment (FMOT) | 第一次看到产品/货架/界面 | P&G 提出 |
| Second Moment (SMOT) | 实际使用/体验产品 | P&G |
| Ultimate Moment (UMOT) | 形成口碑/评价/推荐 | Pete Blackshaw |
| Negative Moment (NMOT) | 出错/投诉/流失 | 服务恢复 |

### 6.2 MoT 与 Persona 的关系

- 不同 Persona 的 MoT 时间点可能完全不同（"效率达人"的 FMOT 在搜索结果页，"社交推荐型"的 FMOT 在朋友分享链接）
- Journey Map 上标注 MoT → 定位设计优先级
- 与 `measurement_toolkit.py` 配合：每个 MoT 绑定一个 metric（如 ZMOT → CTR, FMOT → Trial Rate, SMOT → NPS）

## 七、制图工作坊流程

### 7.1 四步法

| 步骤 | 时长 | 活动 |
|---|---|---|
| 1. Framing | 30 min | 确定 Persona + 场景 + 地图类型 + 范围 |
| 2. Draft Walk | 60 min | 用便签在墙上走一遍旅程（边讨论边贴） |
| 3. Enrich | 45 min | 补充 Thoughts/Feelings/Touchpoints/Pain |
| 4. Prioritize | 30 min | 投票选出 Top 3 Opportunity |

### 7.2 工作坊参与者建议

| 角色 | 为什么需要 |
|---|---|
| PM | 业务视角、优先级 |
| Designer | 用户视角、交互细节 |
| Engineer | 技术可行性、系统约束 |
| CS/Support | 真实用户痛点第一手 |
| 实际用户 1-2 名 | 防止"脑补" |

## 八、从 Journey Map 反向验证 Persona

### 8.1 当 Journey 暴露 Persona 问题

| 信号 | 意味着 |
|---|---|
| 两个"不同 Persona"的旅程几乎一模一样 | 可能应该合并 |
| 一个 Persona 内旅程出现分叉 | 可能应该拆分 |
| 某 Persona 的旅程无法画出（信息不足） | 该 Persona 缺乏数据支撑 |
| 旅程某阶段所有 Persona 都一样 | 该阶段不需要个性化 |

### 8.2 Persona-Journey 闭环

```
Persona Draft → Journey Map (per Persona)
     ↑                    │
     │                    ▼
     └── Persona Refinement ← Journey 暴露的差异/合并信号
```

## 十、反模式

| # | 反模式 | 后果 | 修复 |
|---|---|---|---|
| 1 | 无 Persona 锚定的地图 | "通用用户"旅程谁都不像 | 每张地图必须绑定一个具体 Persona |
| 2 | 只画 Happy Path | 忽略出错/流失/投诉路径 | 必须画至少一条 Failure Path |
| 3 | 地图画完就存档 | 变成装饰品 | 每 Sprint Review 对照地图检查 |
| 4 | 行为+情绪全靠猜 | 数据假设未验证 | 至少 3 次访谈验证每个 Phase 的情绪 |
| 5 | 粒度太细 | 一张图 50+ 步骤读不完 | 先 5-7 Phase 高层，需要时展开子旅程 |
| 6 | 只有前台无后台 | 无法落地改进 | 加 Backstage 行或升级为 Blueprint |
| 7 | 一次性作品 | 两个月后过时 | 指定"地图 Owner"负责季度更新 |

## 本部分核心要点总结

1. **Journey Map 是 Persona 的时间维度延伸**：Persona 说"是谁"，Journey 说"经历了什么"
2. **五行结构（Phases/Actions/Thoughts/Feelings/Touchpoints）是最小可用框架**
3. **Service Blueprint 加 Backstage 才能推动组织变革**
4. **Moments of Truth 定位设计投资优先级**
5. **Journey Map 可以反向验证 Persona 切分是否正确**
6. **地图需要 Owner 和更新节奏**——否则变成"一次性艺术品"
